# Protocol Drivers, Wire Contracts

> Reversa Writer · 2026-10-26 · unit `protocol-drivers` · 🟢 CONFIRMED (generated by running the legacy drivers) · 🟡 INFERRED · 🔴 GAP
> External contract: the BLE GATT write payloads that each controller family accepts. This is the only external interface of LED Union; there is no HTTP API.

## Transport contract 🟢

| Family | Service | Write characteristic | Write mode | Pacing | Max write size |
|---|---|---|---|---|---|
| bledim | `0000fff0-0000-1000-8000-00805f9b34fb` | `…fff1…` (or any writable char in the service) | with response | ≥ 30 ms between ops and between chunks | 20-byte chunks |
| fff0 (ELK/MELK) | `0000fff0-…` | `…fff3…` (or any writable) | without response, falling back to with response | ≥ 5 ms | whole 9-byte frame |
| ffe0 (LED+LAMP) | `0000ffe0-…` | `…ffe1…` (or any writable) | without response, falling back to with response | ≥ 50 ms | whole 9-byte frame |

- The device sends **nothing back** that the app reads; there is no ack contract (BR-30). 🟢
- Handshakes are written once per connection, before any command, **on the normal single-connect path** (see the ffe0 handshake and bledim `onConnect` below). 🟢 Limits: `online` is set before the handshake is queued (`ble.svelte.ts:209-212`), so a racing command could precede a second handshake frame (today every driver sends at most one); concurrent connects are not deduplicated; Debug `sendRaw` bypasses `connect` and writes without a handshake (`ble.svelte.ts:435-440`). [external review R13]

## How to read the tables
- **Every frame below was produced by running `src/lib/protocol/*` under node**, not typed by hand. The script is reproducible: run it with the probe values below.
- Probe values: colour `R=11 G=22 B=33` (hex); percent `42` → `2A`; second percent `58` → `3A`; effect id `5`; output channel byte `2`; sound mode `5`.
- These are **sample frames**. Where a probe appears, that position is the parameter's slot, but not every other byte is a constant: some are computed from the probe (dmx brightness/white 42 also gives `0D` = `scale32(42)`), and BLEDIM frames carry `seq`, a checksum and remembered state. Read the builder in `src/lib/protocol/` to tell constants from derived fields. [external review R14]
- `FF` is the families' "unused / default" filler unless a note says otherwise.
- Hardware status (BR-53): **ffe0 LEDBLE-00 and LEDCAR-01 are verified on devices; BLEDIM static colour is verified.** Everything else matches the vendor apps' bytes but has not been tried on hardware. 🟡

### bledim full-frame encoding 🟢
`55 AA <seq> <cmd> <lenHi> <lenLo> <payload…> <sum>`
- `seq` is a free-running counter, `& FF`, shared by every BLEDIM; the device does not validate it.
- `len` is the payload length, big-endian (`00 48` = 72 for scenes).
- `sum` is `(Σ of every preceding byte) & FF`, sync bytes included.
- Example: `frame(0x80, [01])` with `seq = 00` → `55 AA 00 80 00 01 01 81`. (This one line is **computed by hand** from the formula, because `seq` differs on every run: `55+AA+00+80+00+01+01 = 181`, `& FF = 81`. Every other frame in this file is generated.)
- A scene frame is 6 + 72 + 1 = 79 bytes, written as 20 + 20 + 20 + 19.

Scene payload layout (`0x82`, 72 bytes) 🟢:

| Offset | Meaning | Static colour | Effect | Custom effect |
|---|---|---|---|---|
| 0 | fade flag | 0 | 0 | 0 jump / 1 fade |
| 1 | speed (0..255) | `C0` (192, fixed) | remembered speed | remembered speed |
| 2 | brightness (0..255) | `FF` (fixed; brightness is baked into RGB) | remembered brightness | remembered brightness |
| 3 | colour count | 1 | 1 | n ≤ 14 |
| 4 | scene slot | 0 | 0 | 0 |
| 6 | strobe | 0 | remembered strobe (0) | remembered strobe (0) |
| 14 | effect | `00` | `id \| 80` (chase bit) | `FF` (no effect; the list plays) |
| 16 + 4i .. 19 + 4i | colour i as `W R G B` | `00 R G B` (white scene: `W 00 00 00`) | `00 FF FF FF` | `00 R G B` each |

`0x88` payload: `FF` (free scene) · `01` (commit) · speed · brightness · strobe · `00`.

## Notes and anomalies found while generating the tables

| # | Observation | Status |
|---|---|---|
| C1 | **F18 · LEDCAR-02 (`dmxs`) carries the output channel byte only in the effect frame.** Power, rgb, brightness, speed and sound are byte-identical for `LED 1` and `LED 2`; that both physical outputs then react is 🟡 unverified on hardware [external review R11]. The UI offers two output cards for LEDCAR-02 (`outputsFor`), but only the effect select actually targets one. | 🟢 code fact; 🔴 whether the vendor app also does this needs checking in the decompiled Java (G2 class) |
| C2 | On the ffe0 `ble` layout, **power defaults byte 7 to `00`**, while rgb, brightness, speed, effect and soundMode default to `FF`. On LEDBLE-02, `00` = all outputs. | 🟢 code; 🔴 meaning on other `ble` models (G2) |
| C3 | **F19 ·** `soundSensitivity` on **`smart` and `pho`** falls through to the `ble` envelope (`7E FF 07 … EF`). The DeviceCard shows the sensitivity slider for every ffe0 device, so LEDSMART and LEDPHO receive a foreign-layout frame. | 🟢 code defect (new); 🟡 the vendor app may simply have no sensitivity command there, in which case the slider should be hidden |
| C4 | `cct` on `dmx`, `smart` and `like` falls through to the `ble` envelope. It is unreachable from the UI because `caps.cct` is false on those layouts. | 🟢 latent |
| C5 | `white` exists on every ffe0 layout, though `caps.white` is true only on `dmxs` and `smart`. The `ble` frame `7E FF 05 01 w FF FF FF EF` is unreachable from the UI. | 🟢 latent |
| C6 | `dmx` power differs between LEDDMX (`7B 04 04 v …`) and LEDCAR-01 SPI (`7B FF 04 v …`). | 🟢 vendor quirk, preserved |
| C7 | LEDBLE-03 differs from LEDBLE only in the effect frame; its power, colour, brightness and custom-effect frames are the `ble` ones. | 🟢 |
| C8 | LEDSTAGE / LEDLIGHT: power has no channel byte and no `00` slot; the custom effect writes DIY slot `00` without an index and has no start frame. | 🟢 |
| C9 | fff0 `soundMode` ORs `80` into the mode, and its length byte is `07` on MELK, `05` on ELK. | 🟢 |
| C10 | The white-only layouts (`sun`, `like`) map `rgb(11,22,33)` to `white(round(avg/255·100)) = white(13)` → `0D`. | 🟢 |

## Reproducing these tables
The generator is saved next to this file as `gen-contracts.mjs`. Run it **from the repository root** (it resolves `src/` from the working directory):
```bash
node --experimental-strip-types _reversa_sdd/protocol-drivers/gen-contracts.mjs
```
Its first 103 lines reproduce the "Frames per family" tables above (verified 2026-10-26). A single frame can also be checked directly, e.g.:
```bash
node --experimental-strip-types -e "import('./src/lib/protocol/ffe0.ts').then(m => console.log([...m.ffe0.rgb(0x11,0x22,0x33,'LEDDMX-02-1')].map(x=>x.toString(16).padStart(2,'0')).join(' ')))"
```
Recommended: commit an equivalent script under `tools/` and diff its output in CI. It would catch byte drift that the 39 hand-written tests do not cover (see `tooling/`).
